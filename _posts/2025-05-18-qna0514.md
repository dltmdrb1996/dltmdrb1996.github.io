### **I. 웹 통신의 근간 (The Heart of Web Communication)**

#### **1.1. HTTP (HyperText Transfer Protocol)**

HTTP는 클라이언트와 서버가 웹에서 데이터를 주고받기 위해 사용하는 핵심적인 **애플리케이션 계층(OSI 7계층) 프로토콜**입니다. 그 근본적인 특징은 **'무상태성(Stateless)'**과 **'비연결성(Connectionless)'**입니다.

**1) HTTP 메시지 구조**

*   **요청(Request) 메시지 (Client → Server)**
    ```http
    GET /users/123 HTTP/1.1
    Host: api.example.com
    User-Agent: Chrome/108.0.0.0
    Accept: application/json
    Authorization: Bearer <JWT_TOKEN>
    ```
  *   **시작줄 (Start Line):** HTTP 메소드, 요청 대상(경로), HTTP 버전으로 구성됩니다.
  *   **헤더 (Headers):** Key: Value 형태의 메타데이터로, 요청에 대한 부가 정보를 담습니다.
  *   **본문 (Body):** `POST`, `PUT` 등의 요청 시 전송할 실제 데이터(Payload)가 담깁니다.

*   **응답(Response) 메시지 (Server → Client)**
    ```http
    HTTP/1.1 200 OK
    Content-Type: application/json
    Content-Length: 157
    Access-Control-Allow-Origin: *

    { "id": 123, "name": "John Doe" }
    ```
  *   **상태줄 (Status Line):** HTTP 버전, 상태 코드(예: 200), 상태 텍스트(예: OK)로 구성됩니다.
  *   **헤더 (Headers):** 응답에 대한 부가 정보를 담습니다.
  *   **본문 (Body):** 클라이언트에게 전달할 실제 데이터가 담깁니다.

**2) 심층 Q&A: DNS 조회는 매 요청마다 발생합니까?**
**A:** 아닙니다. 성능 최적화를 위해 여러 단계의 **DNS 캐시**를 활용합니다.
1.  **브라우저 캐시:** 브라우저가 최근 조회한 도메인 정보를 자체적으로 저장합니다.
2.  **운영체제(OS) 캐시:** OS 수준에서 관리하는 캐시(Stub Resolver)를 확인합니다.
3.  **라우터 캐시:** 로컬 네트워크의 라우터가 보유한 DNS 캐시를 조회합니다.
4.  **Recursive DNS 서버 (ISP DNS):** 위 로컬 캐시에 모두 없는 경우, 비로소 외부 DNS 서버에 질의합니다. 이 서버는 전 세계 도메인에 대한 거대한 캐시 역할을 수행합니다.

이 캐시 정보는 **TTL(Time To Live)** 값에 따라 유효 기간이 결정되며, 이 때문에 DNS 레코드 변경 시 전파 지연이 발생할 수 있습니다.

#### **1.2. 상태 관리: 쿠키, 세션, JWT**

HTTP의 '무상태성'을 보완하여 사용자 상태(예: 로그인)를 유지하기 위한 기술입니다.

*   **쿠키 (Cookie):** 클라이언트 측(브라우저)에 저장되는 작은 텍스트 데이터입니다. 서버가 `Set-Cookie` 헤더로 전달하면, 브라우저는 이후의 모든 요청에 `Cookie` 헤더를 자동으로 포함시켜 전송합니다. 보안을 위해 `HttpOnly`, `Secure`, `SameSite` 속성 설정이 매우 중요합니다.

*   **세션 (Session):** 민감한 사용자 정보를 서버 측에 저장하고, 클라이언트에게는 그 정보를 식별하기 위한 고유 ID(**세션 ID**)만 쿠키로 전달하는 방식입니다.
  *   **세션 저장소:** WAS 메모리(서버 재시작 시 휘발, 확장성 문제), DB(영속성 보장, 부하 증가), **인메모리 데이터 그리드(Redis 등)**가 사용됩니다. 현대적인 아키텍처에서는 속도, 영속성, 확장성을 모두 고려하여 Redis를 중앙 세션 저장소로 사용하는 것이 일반적입니다.

**심층 Q&A: 쿠키-세션 방식과 헤더에 JWT를 사용하는 방식의 근본적인 차이는 무엇입니까?**
**A:** 가장 큰 차이점은 **서버의 상태 저장 유무(Statelessness)**입니다.
*   **쿠키-세션 방식 (Stateful):** 서버는 '세션 저장소'라는 **상태를 유지**해야 합니다. 서버를 여러 대로 확장(Scale-out)하면, 이 세션 정보를 모든 서버가 공유하기 위한 추가적인 구성(예: Sticky Session, Redis)이 필요합니다.
*   **헤더-JWT 방식 (Stateless):** **서버는 아무것도 저장하지 않습니다.** 서버는 클라이언트가 `Authorization` 헤더에 담아 보낸 JWT의 **서명(Signature)만 검증**합니다. 서명이 유효하다면 토큰 안의 정보를 신뢰하고 사용자를 식별합니다. 이 특성은 수평적 확장이 필수적인 **MSA(Microservice Architecture) 환경에 극도로 용이**하여 표준처럼 사용됩니다.
*   **보안 트레이드오프:** 세션은 서버에서 강제로 무효화하기 쉽지만, JWT는 한번 탈취되면 만료 시간 전까지는 유효하다는 단점이 있습니다. (이를 보완하기 위해 **Refresh Token 패턴**, 토큰 블랙리스트 관리 등의 기법을 사용합니다.)

#### **1.3. CORS (Cross-Origin Resource Sharing)**

브라우저의 **'동일 출처 정책(Same-Origin Policy, SOP)'**으로 인해 발생하는 문제를 해결하기 위한 표준 메커니즘입니다.

*   **SOP란?** 프로토콜, 호스트, 포트가 모두 동일해야 '동일 출처'로 인정하는 브라우저의 보안 정책입니다. 하나라도 다르면 '다른 출처(Cross-Origin)'로 간주되어, 스크립트 기반의 HTTP 요청이 기본적으로 차단됩니다.
*   **동작 원리:** 클라이언트-서버 분리 아키텍처에서 브라우저의 JavaScript가 다른 출처의 API 서버로 요청을 보낼 때, 브라우저는 이 요청을 가로채고 서버의 응답에 `Access-Control-Allow-Origin`과 같은 CORS 관련 헤더가 있는지 확인합니다. 허가가 없으면 응답 데이터를 폐기하고 에러를 발생시킵니다.
*   **프리플라이트 요청 (Preflight Request):** `PUT`, `DELETE` 혹은 커스텀 헤더를 포함하는 '복잡한 요청'의 경우, 브라우저는 본 요청을 보내기 전에 **`OPTIONS`** 메소드를 사용한 예비 요청을 먼저 보내 서버가 해당 요청을 수락하는지 확인합니다. 백엔드 개발자는 이 `OPTIONS` 요청에 대해 올바른 CORS 헤더로 응답해야 합니다.

### **II. 통신의 기반과 성능 최적화**

#### **2.1. 전송 계층: TCP vs UDP**

*   **TCP (Transmission Control Protocol):** **신뢰성**을 중시하는 **연결 지향형** 프로토콜입니다. 3-Way Handshake로 연결을 수립하고, 데이터의 순서 보장, 흐름 제어, 혼잡 제어, 오류 감지 및 재전송을 통해 데이터가 정확하게 전달됨을 보장합니다.
*   **UDP (User Datagram Protocol):** **속도**를 중시하는 **비연결형** 프로토콜입니다. 신뢰성 보장을 위한 절차를 모두 생략하여 매우 빠르지만, 데이터 유실이나 순서 뒤바뀜이 발생할 수 있습니다. 실시간 스트리밍, DNS 등에 사용됩니다.

**심층 Q&A: 오류/흐름 제어를 왜 IP가 아닌 TCP가 담당합니까?**
**A:** 계층별 책임의 범위가 다르기 때문입니다.
*   **IP (네트워크 계층):** **'개별 패킷'**을 목적지 컴퓨터까지 **'최선 노력(Best-Effort)'**으로 전달하는 데만 집중합니다. 각 패킷의 유실이나 순서에는 책임지지 않습니다.
*   **TCP (전송 계층):** 신뢰성 없는 IP 위에서, **'전체 데이터 스트림'**이 출발지 애플리케이션에서 목적지 애플리케이션까지 **'완벽하고 순서대로'** 도착하는 것을 책임집니다. 이를 위해 자체적으로 오류/흐름/순서 제어 로직을 구현한 것입니다.

**심층 Q&A: TCP는 세그먼트 하나마다 응답(ACK)을 기다립니까?**
**A:** 아닙니다. **슬라이딩 윈도우(Sliding Window)** 메커니즘을 사용합니다. 송신 측은 ACK를 기다리지 않고 '윈도우 크기'만큼의 세그먼트를 연속으로 전송할 수 있습니다. 수신 측은 받은 데이터에 대해 매번 응답하는 대신, **누적 ACK(Cumulative ACK)**를 통해 "여기까지 순서대로 잘 받았다"고 효율적으로 응답합니다. 이를 통해 네트워크 회선을 쉬지 않고 사용하여 전송 효율을 극대화합니다.

#### **2.2. HTTP 프로토콜의 진화**

*   **HTTP/1.1:** **지속적 연결(Keep-Alive)**을 도입하여 TCP 연결을 재사용함으로써 성능을 크게 향상시켰습니다. 하지만 단일 연결 내에서 요청-응답이 순차적으로 처리되어야 하는 **HOLB(Head-of-Line Blocking)** 문제가 있었습니다.
*   **HTTP/2:** **다중화(Multiplexing)**를 통해 단일 TCP 연결 내에 여러 개의 독립적인 **스트림(Stream)**을 만들어 HOLB를 해결했습니다. 각 스트림의 데이터 프레임들이 **인터리빙(Interleaving)**되어 전송되므로, 특정 응답이 지연되어도 다른 응답을 블로킹하지 않습니다.
*   **HTTP/3:** TCP가 아닌, UDP 기반의 **QUIC** 프로토콜을 사용합니다. 이는 TCP 계층에서 발생하는 HOLB(패킷 하나 유실 시 전체 스트림이 지연되는 문제)까지 해결하여, 네트워크 환경이 불안정한 모바일 등에서 더 빠르고 안정적인 통신을 제공합니다.

### **III. 실시간 및 비동기 통신 아키텍처**

#### **3.1. WebSocket**

클라이언트와 서버 간의 지속적인 **양방향(Full-duplex)** 통신 채널을 제공하는 프로토콜입니다. 최초 연결 시 HTTP 핸드셰이크를 통해 연결을 '업그레이드'하는 방식으로 시작됩니다.

**심층 Q&A: WebSocket의 양방향 동시 통신은 어떻게 가능합니까?**
**A:** OS 커널 수준에서 **독립된 송신(Send) 버퍼와 수신(Receive) 버퍼**를 사용하고, 이를 매우 빠른 속도로 **시분할(Time-sharing)** 방식으로 처리함으로써 구현됩니다. 물리적인 회선은 하나이므로 패킷들은 시분할 방식으로 회선을 **경쟁적으로 선점**하여 사용하지만, 이 전환이 워낙 빨라 논리적인 동시 통신이 가능해집니다.

**심층 Q&A: 대규모 실시간 연결은 어떻게 관리하고 메시지를 전파합니까?**
**A:** 중앙 메시지 브로커(주로 **Redis Pub/Sub**)를 활용한 아키텍처를 사용합니다.
1.  **연결 관리:** 각 애플리케이션 서버는 자신에게 접속된 WebSocket 클라이언트의 연결 정보를 메모리(예: `ConcurrentHashMap`)에 유지합니다.
2.  **메시지 발행:** 특정 서버에서 이벤트가 발생하면, 연결된 클라이언트에게 직접 메시지를 보내는 대신 Redis 채널에 메시지를 **발행(Publish)**합니다.
3.  **수신 및 전파:** 모든 애플리케이션 서버는 해당 Redis 채널을 **구독(Subscribe)**하고 있다가 메시지를 수신합니다. 이후 각 서버는 자신이 관리하는 클라이언트 중에서 해당 메시지를 받아야 할 대상에게만 최종적으로 메시지를 전송합니다.
4.  **성능 확장:** 이 구조에서 Redis에 대한 부하를 줄이기 위해, 각 서버에 **로컬 캐시(예: Caffeine)**를 두고 자주 조회되는 정보(예: 채팅방 멤버 목록)를 저장합니다. 데이터 변경 시에는 별도의 관리 채널(Pub/Sub)을 통해 모든 서버의 로컬 캐시를 **무효화(Invalidate)**하는 전략을 사용합니다. Redis 자체의 부하가 커지면 **Redis 클러스터**로 확장하며, 이때 관련 데이터를 같은 노드에 위치시키는 **해시 태그(`{roomId}`)** 사용이 중요합니다.

#### **3.2. Webhook & SSE**

*   **Webhook:** 특정 이벤트가 발생했을 때, 한 시스템이 다른 시스템의 API 엔드포인트(Webhook URL)로 **먼저 HTTP POST 요청을 보내** 데이터를 전달하는 아키텍처 패턴입니다. 주기적으로 상태를 확인하는 폴링(Polling) 방식의 비효율성을 해결하며, 결제 시스템 연동이나 CI/CD 파이프라인 자동화 등에 널리 사용됩니다.
*   **SSE (Server-Sent Events):** 서버에서 클라이언트로의 **단방향 데이터 스트리밍**이 필요할 때 사용하는 경량 기술입니다. 표준 HTTP 기반으로 동작하여 구현이 간단하며, 뉴스 피드나 실시간 알림처럼 클라이언트가 받기만 하면 되는 경우에 매우 효과적입니다.

### **IV. 네트워크 아키텍처 및 인프라**

#### **4.1. 로드 밸런서와 리버스 프록시**

*   **리버스 프록시 (Reverse Proxy):** 클라이언트의 요청을 대신 받아 내부 서버(WAS)에 전달하는 '관문' 역할을 합니다. SSL 암호화/복호화, 캐싱, 압축, 요청 로깅, 보안 강화(WAF) 및 **로드 밸런싱** 등 다양한 기능을 수행합니다. (예: Nginx)
*   **로드 밸런서 (Load Balancer):** 서버에 가해지는 트래픽 부하를 여러 대의 서버에 균등하게 분산시켜 **가용성(High Availability)**과 **확장성(Scalability)**을 확보하는 장치 또는 소프트웨어입니다.

**심층 Q&A: AWS ELB와 Spring Cloud Gateway가 왜 둘 다 필요한가요?**
**A:** 서로 다른 계층의 문제를 해결하기 때문입니다.
*   **AWS ELB (Edge Proxy):** 시스템의 가장 최전방(Edge)에서 인터넷 트래픽을 수신하여 내부의 API 게이트웨이 인스턴스들에게 분산시키는 **인프라 레벨**의 역할을 합니다. 주로 L4/L7 로드 밸런싱, SSL 종료, DDoS 방어 등을 담당합니다.
*   **Spring Cloud Gateway (Microservice Proxy):** ELB 뒤에서 MSA의 진입점 역할을 하는 **애플리케이션 레벨**의 게이트웨이입니다. 요청의 헤더나 본문을 분석하여 적절한 마이크로서비스로 라우팅하고, 중앙화된 인증/인가, 로깅, 요청/응답 변환 등 복잡하고 지능적인 정책을 처리합니다.

**심층 Q&A: AWS ELB와 같은 로드 밸런서는 단일 장애점(SPOF)이 아닌가요?**
**A:** 아닙니다. 사용자에게는 단일 도메인 주소로 보이지만, 실제로는 **내부적으로 고도로 분산되고 이중화된 시스템**입니다. 트래픽에 따라 자동으로 확장/축소(Auto Scaling)되며, 여러 가용 영역(Multi-AZ)에 걸쳐 배포되어 있습니다.

#### **4.2. CDN (Content Delivery Network)**

이미지, 동영상, CSS/JS 등 **정적 콘텐츠**를 전 세계에 분산된 **엣지 서버(Edge Server)**에 캐싱해두고, 사용자와 물리적으로 가장 가까운 서버에서 콘텐츠를 전송하여 로딩 속도를 획기적으로 향상시키고 원본(Origin) 서버의 부하를 줄이는 기술입니다.

**심층 Q&A: CDN은 S3의 데이터를 미리 복제해두는 방식인가요?**
**A:** 아닙니다. 대부분의 CDN은 사전에 모든 데이터를 복제하는 '푸시(Push)' 방식이 아닌, 요청이 발생했을 때 데이터를 가져오는 **'풀(Pull)' 방식의 캐싱(Caching) 모델**을 사용합니다. 요청이 발생하면 비로소 원본(S3)에서 데이터를 가져와 일정 시간(TTL) 동안만 임시 보관합니다.

#### **4.3. 무중단 배포 (Zero-Downtime Deployment)**

로드 밸런서를 이용해 서비스 중단 없이 새로운 버전을 배포하는 전략입니다.
*   **롤링 배포 (Rolling Update):** 서버 인스턴스를 하나씩 점진적으로 교체합니다. 추가 리소스가 필요 없어 비용 효율적이지만, 배포 중 신/구 버전이 공존하므로 호환성 관리가 중요합니다.
*   **블루/그린 배포 (Blue/Green Deployment):** 신버전 환경(Green)을 기존 환경(Blue)과 별도로 완벽하게 구축한 후, 로드 밸런서의 트래픽을 한 번에 전환합니다. 매우 안전하고 즉시 롤백이 가능하지만, 리소스 비용이 2배로 듭니다.
*   **카나리 배포 (Canary Deployment):** 신버전을 아주 일부 사용자(예: 1% 트래픽)에게만 먼저 공개하여 안정성을 검증하고, 문제가 없으면 점진적으로 트래픽을 확대합니다. 가장 안전하지만 정교한 트래픽 제어와 모니터링이 필요하여 관리 복잡도가 높습니다.

### **V. 심화 아키텍처 패턴**

#### **5.1. TLS/SSL 핸드셰이크와 세션 재활용**

HTTPS 통신의 핵심으로, **대칭키 암호화(빠른 데이터 암호화)**와 **비대칭키 암호화(안전한 키 교환)**의 장점을 결합한 하이브리드 암호화 방식입니다.
*   **TLS 핸드셰이크:** 실제 데이터 통신 전에, 비대칭키 방식을 사용하여 서버의 신원을 인증서로 검증하고, 양측이 데이터를 암호화하는 데 사용할 **대칭키(세션 키)를 안전하게 교환(생성)**하는 과정입니다.
*   **세션 재활용 (Session Resumption):** 한번 맺은 TLS 보안 세션은 이후의 TCP 연결에서 재활용될 수 있습니다. 이를 통해 매번 비용이 큰 핸드셰이크 과정을 반복하는 비효율을 줄이고 통신 시작 시간을 단축합니다.

#### **5.2. 서비스 메시 (Service Mesh)**

MSA 환경에서 서비스 간의 통신(East-West Traffic)을 전담하는 별도의 **인프라 계층**입니다.
*   **구조:** 각 서비스 파드(Pod)에 **사이드카 프록시(Sidecar Proxy, 예: Envoy)**를 함께 배포(Data Plane)하고, 이를 **컨트롤 플레인(Control Plane, 예: Istio)**이 중앙에서 정책에 따라 제어합니다.
*   **원리:** OS의 네트워킹 기능(**iptables** 등)을 이용해 파드의 모든 네트워크 트래픽을 투명하게 가로채 사이드카 프록시를 거치도록 만듭니다.
*   **역할:** 개발자가 비즈니스 로직에만 집중할 수 있도록, 애플리케이션 코드 수정 없이 동적 라우팅, 서킷 브레이커, 타임아웃/재시도, 서비스 간 상호 TLS(mTLS) 암호화, 분산 추적 등 복잡한 네트워크 제어 기능을 인프라 레벨에서 제공합니다.

#### **5.3. API 게이트웨이와 BFF 패턴**

API 게이트웨이를 설계하는 아키텍처 패턴입니다.
*   **일반적인 API 게이트웨이:** 모든 종류의 클라이언트(웹, 모바일 등)를 위한 단일 진입점 역할을 합니다. "One-Size-Fits-All" 방식으로, 다양한 클라이언트의 각기 다른 요구사항을 모두 만족시키기 어려울 수 있습니다.
*   **BFF (Backend For Frontend) 패턴:** 웹, iOS, Android 등 각 프론트엔드(클라이언트 경험)를 위한 **별도의 맞춤형 백엔드(게이트웨이)**를 두는 방식입니다. 각 클라이언트에 최적화된 API를 제공(데이터 조합, 필드 제거 등)하여 성능을 높이고, 프론트엔드 팀의 자율성과 개발 속도를 향상시킬 수 있는 장점이 있습니다.
