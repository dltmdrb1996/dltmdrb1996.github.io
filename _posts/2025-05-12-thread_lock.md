## **시스템 동시성 제어 **

### 0. 들어가며: 왜 동시성 제어가 중요한가?

현대 컴퓨팅 시스템은 제한된 하드웨어 자원, 특히 **CPU 코어 수의 한계**라는 근본적인 제약 하에서 이를 최대한 활용하여 여러 작업을 동시에 처리하고 사용자에게 빠른 응답성을 제공해야 합니다. **동시성(Concurrency)** 프로그래밍은 이러한 요구를 만족시키는 핵심 기술이지만, 여러 실행 흐름(스레드)이 **공유된 변경 가능한 상태(Shared Mutable State)**, 즉 **공유 자원(Shared Resource)**에 동시에 접근할 때, 특히 다중 코어 환경에서 물리적으로 동시에 접근할 때 문제가 발생할 수 있습니다. 스레드의 실행 순서가 CPU 스케줄링, 인터럽트 타이밍, 그리고 **코어 간의 미묘한 상호작용(예: 캐시 일관성 문제)** 등으로 인해 예측 불가능하기 때문에, 데이터 값이 의도치 않게 변경되거나 깨지는 **경쟁 상태(Race Condition)**가 발생하여 프로그램 오작동이나 **데이터 부정합(Data Inconsistency)**을 초래할 수 있습니다.

이러한 문제를 방지하고 여러 스레드가 안전하게 공유 자원에 접근하도록 보장하는 것, 즉 코드의 **스레드 안전성(Thread Safety)**을 확보하는 것이 필수적입니다. 이를 위해 운영체제(OS)와 프로그래밍 언어는 다양한 동기화 메커니즘(락, 세마포어 등)을 제공하며, 이들은 CPU가 제공하는 **원자적 연산(Atomic Operations)**과 **메모리 장벽(Memory Barriers)** 같은 하드웨어 수준의 지원에 의존합니다. 더 나아가, 동시에 여러 락을 사용하거나 스레드 우선순위가 얽힐 경우 **교착 상태(Deadlock)**나 **우선순위 역전(Priority Inversion)**과 같은 더 복잡한 문제가 발생할 수도 있으며, 이는 제한된 CPU 자원을 효율적으로 사용하려는 시도에서 파생되는 또 다른 과제입니다. 심지어, 여러 코어가 각자의 캐시에 데이터를 저장할 때 발생하는 **캐시 일관성(Cache Coherency)** 문제나, 관련 없는 데이터가 같은 캐시 라인에 위치하여 발생하는 **거짓 공유(False Sharing)** 현상 등은 CPU 코어의 한계와 분산된 캐시 시스템으로 인해 발생하는 미묘하지만 성능에 큰 영향을 미치는 문제입니다.

이 문서는 동시성의 기초가 되는 OS의 시분할 멀티태스킹 원리부터 시작하여, 프로세스와 스레드의 개념과 차이, OS 스케줄링 방식(특히 멀티코어 환경에서의 고려사항 포함), 동시성 문제 해결의 핵심인 다양한 락(Lock) 메커니즘의 종류와 내부 구현 원리, 관련 문제점(우선순위 역전, 교착 상태, 스핀락의 CPU 낭비)과 해결책을 상세히 다룹니다. 또한, CPU 아키텍처 수준에서의 동시성 지원(원자적 연산, 메모리 모델, 캐시 일관성 프로토콜)을 이해하고, C 언어의 메모리 관리 방식과 Java의 구체적인 락 구현(AQS, `synchronized`의 내부 동작)을 깊이 있게 탐구합니다. 마지막으로 OS 스레드의 한계(특히 코어 수 대비 스레드 생성 비용 및 관리 오버헤드)를 극복하기 위한 최신 동시성 모델인 가상 스레드(Virtual Threads)와 코루틴(Coroutines)까지 포괄적으로 정리하여, 시스템의 동시성 제어에 대한 깊이 있는 이해를 제공하는 것을 목표로 합니다. CPU 코어 수의 한계라는 본질적인 제약 조건이 어떻게 시스템 전반의 동시성 관리 전략과 기술 발전에 영향을 미치는지 그 파생 효과들을 중심으로 내용을 확장했습니다.

### 1. 운영체제 기본 원리: 동시성의 기반

#### 1.1 동시성(Concurrency) vs 병렬성(Parallelism)

*   **동시성**: 여러 작업이 **논리적으로 겹쳐지는 시간 동안** 진행되는 것을 의미합니다. 싱글 코어 CPU에서도 운영체제의 시분할(Time-Sharing) 기법을 통해 여러 작업을 번갈아 가며 빠르게 실행시켜 동시에 처리되는 것처럼 보이게 할 수 있습니다. 마치 한 명의 요리사가 여러 요리를 동시에 진행하는 것과 같습니다. 핵심은 '관리'와 '작업 전환'입니다.
*   **병렬성**: 여러 작업이 **물리적으로 정확히 같은 시간**에 여러 개의 CPU 코어에서 동시에 실행되는 것을 의미합니다. 이는 **멀티 코어 프로세서**와 같은 하드웨어 지원이 필수적입니다. 여러 명의 요리사가 각자 다른 요리를 동시에 만드는 것과 같습니다. 핵심은 '동시 실행'입니다. CPU 코어 수가 병렬성의 직접적인 한계를 결정합니다.
*   멀티태스킹과 멀티스레딩은 시스템 환경(싱글/멀티 코어)에 따라 동시성 또는 병렬성을 제공할 수 있습니다. 멀티 코어 시스템에서 동시성 프로그램은 병렬적으로 실행될 가능성을 가지며, 이로 인해 공유 자원 접근 문제가 더욱 첨예해집니다.

#### 1.2 CPU 멀티태스킹의 발전

1.  **배치 처리 (Batch Processing)**: 초기 방식으로, 하나의 작업(Job)이 제출되면 완료될 때까지 CPU를 독점. 작업 중 I/O 대기 시 CPU는 다른 작업을 하지 못하고 유휴(idle) 상태가 됨. (단일 코어 CPU 활용도 저하)
2.  **멀티프로그래밍 (Multiprogramming)**: CPU 효율을 높이기 위해 여러 작업을 메모리에 적재. 한 작업이 I/O 대기 상태가 되면 OS가 다른 작업으로 CPU 제어권을 넘김 (컨텍스트 스위치). 이는 I/O 발생 등 특정 이벤트에 의해서만 전환이 일어나는 **비선점적(Non-preemptive) 또는 협조적(Cooperative)** 방식. 하나의 작업이 CPU를 양보하지 않으면 다른 작업은 실행될 수 없음.
3.  **시분할 / 선점형 멀티태스킹 (Time-Sharing / Preemptive Multitasking)**: 현재 대부분의 OS 방식. OS가 **타이머 인터럽트**를 이용하여 주기적으로 실행 중인 작업의 상태를 확인하고, 할당된 시간(타임 슬라이스, Quantum)이 다 되었으면 **강제로 제어권을 빼앗아(선점)** 다른 작업에게 CPU를 할당함. 이를 통해 여러 사용자가 동시에 시스템을 사용하거나 여러 애플리케이션이 동시에 실행되는 것처럼 느끼게 하여 **공정한 자원 분배**와 **빠른 응답성**을 보장. 멀티 코어 환경에서는 각 코어가 독립적으로 또는 협력적으로 스케줄링을 수행하며, 작업들을 여러 코어에 분배합니다.
    *   *(참고) 네트워크 TDM*: 통신 회선의 대역폭을 시간 슬롯으로 나누는 물리 계층 기술로, OS의 CPU 시간 분할보다 훨씬 이전(1894년경)에 정립된 개념.

#### 1.3 프로세스(Process)와 스레드(Thread)

*   **프로세스**:
    *   **정의**: 실행 중인 프로그램의 인스턴스.
    *   **자원 소유 단위**: 자신만의 독립된 가상 주소 공간, 파일 디스크립터 테이블, 시스템 자원(메모리, 파일 등) 할당 받음. 다른 프로세스의 자원에 직접 접근 불가 (격리성). 이는 멀티코어 환경에서 각 프로세스가 다른 코어에서 실행될 때 데이터 격리를 보장하는 중요한 특징입니다.
    *   **역할**: 스레드가 실행될 수 있는 환경(컨테이너) 제공.
*   **스레드**:
    *   **정의**: 프로세스 내에서 실행되는 제어 흐름(실행 단위).
    *   **CPU 스케줄링 단위**: OS 스케줄러는 스레드 단위로 CPU 시간을 할당함. (특히 커널 수준 스레드)
    *   **자원 공유**: 같은 프로세스 내의 다른 스레드들과 코드(Code), 데이터(Data), 힙(Heap) 영역 메모리 및 열린 파일 등을 **공유**함. 이 공유 특성 때문에 멀티코어에서 병렬 실행 시 동기화 문제가 발생합니다.
    *   **독립적 실행 상태**: 자신만의 프로그램 카운터(PC), 레지스터 세트, **스택(Stack)** 영역을 가짐. 스택에는 함수 호출 정보, 지역 변수 등이 저장됨.

#### 1.4 사용자 수준 스레드 vs 커널 수준 스레드

*   **커널 수준 스레드 (Kernel-Level Thread, KLT)**:
    *   **관리 주체**: 운영체제(OS) 커널. 커널이 각 스레드의 생성, 관리, 스케줄링을 직접 담당.
    *   **특징**: 스레드 관련 작업(생성, 동기화, 스케줄링) 시 시스템 콜(커널 모드 전환) 필요하여 오버헤드 발생. 하나의 스레드가 블록(예: I/O 대기)되어도 OS는 해당 프로세스의 다른 스레드를 다른 CPU 코어에 스케줄링하거나, 현재 코어에서 다른 프로세스의 스레드를 스케줄링할 수 있음. **멀티 코어 환경에서 병렬 실행 가능**하여 CPU 코어들을 효과적으로 활용.
    *   **사용**: 현대 대부분의 OS(Linux, Windows, macOS) 및 Java 표준 스레드(`java.lang.Thread`)가 이 방식을 사용 (1:1 모델 - 하나의 사용자 스레드가 하나의 커널 스레드에 매핑).
*   **사용자 수준 스레드 (User-Level Thread, ULT)**:
    *   **관리 주체**: 사용자 공간의 스레드 라이브러리. OS 커널은 이 스레드의 존재를 알지 못하고, 라이브러리가 스레드 생성, 스케줄링, 동기화를 모두 처리.
    *   **특징**: 커널 개입 없이 스레드 작업(생성, 스위칭)이 이루어지므로 매우 빠르고 오버헤드가 적음. 하지만 라이브러리가 실행되는 프로세스 내의 (하나의) 커널 스레드가 블로킹 시스템 콜을 호출하면, 커널은 해당 커널 스레드 전체를 블록시키므로 그 위에서 동작하는 모든 사용자 수준 스레드가 함께 멈춤 (M:1 모델의 한계). **멀티 코어 활용 불가** (단일 커널 스레드 위에서 동작하므로 병렬성 없음). M:N 모델(다수의 사용자 스레드를 다수의 커널 스레드에 매핑)은 이론적으로 멀티코어 활용이 가능하나 구현 복잡성으로 인해 널리 사용되지 않음.
    *   **사용**: 과거 일부 시스템(예: Green Threads), 특정 언어의 코루틴 라이브러리 구현 방식, 경량 동시성 모델(가상 스레드 내부 관리 방식과 유사성) 등.

#### 1.5 컨텍스트 스위칭 (Context Switching)

*   **정의**: CPU가 현재 실행 중인 작업(프로세스 또는 스레드)에서 다른 작업으로 전환하는 과정. 이 과정은 CPU 시간을 효율적으로 나누어 쓰기 위한 필수 작업이지만, 그 자체로 오버헤드.
*   **과정**:
    1.  현재 작업의 실행 상태(CPU 레지스터 값, 프로그램 카운터, 스택 포인터 등)를 해당 작업의 제어 블록(PCB 또는 TCB)에 저장(Save).
    2.  다음 실행할 작업의 제어 블록에서 저장된 상태를 로드(Restore)하여 CPU 레지스터 등에 적재.
    3.  다음 작업의 실행 시작.
*   **비용 차이**:
    *   **프로세스 간**: 비용 높음. 저장/복원할 상태 정보가 많고, 특히 **가상 메모리 공간 전환**(페이지 테이블 포인터 레지스터(예: CR3) 변경, TLB(Translation Lookaside Buffer) 내용 무효화 또는 플러시) 작업이 큰 오버헤드를 유발. 멀티코어 환경에서는 특정 코어의 TLB뿐 아니라 다른 코어들의 TLB 항목도 관련될 경우 **TLB shootdown**이라는 추가적인 인터럽트와 동기화 비용 발생 가능.
    *   **같은 프로세스 내 스레드 간 (커널 수준)**: 비용 상대적으로 낮음. **동일한 가상 주소 공간을 공유**하므로 페이지 테이블 교체나 TLB 플러시 작업이 불필요. 스레드 고유의 레지스터, PC, 스택 포인터 등 최소한의 정보만 저장/복원하면 됨. 하지만 여전히 커널 모드 전환 비용은 존재.

#### 1.6 OS 스케줄링

*   **목표**: CPU 이용률, 처리량, 응답 시간, 대기 시간, 공정성 등 다양한 지표를 최적화하는 것. 멀티코어 환경에서는 **코어 간 부하 분산(Load Balancing)**, **코어 친화도(CPU Affinity)**, **전력 효율성** 등도 중요한 고려 사항.
*   **주체 및 단위**: OS 커널의 스케줄러가 **스레드**(커널 수준 스레드) 단위로 CPU 할당 결정.
*   **Linux CFS (Completely Fair Scheduler)**:
    *   **관리 단위**: `task_struct` (프로세스와 스레드 모두 동일 구조체 사용, 스레드가 기본 단위).
    *   **핵심 원리**: **가상 실행 시간(vruntime)** 개념 도입. 각 태스크가 실제로 CPU를 사용한 시간을 기반으로 vruntime을 증가시키며, 런큐(Run Queue - **각 CPU 코어마다 독립적으로 존재**하거나 공유될 수 있음. 현대는 주로 per-CPU 런큐) 내에서 vruntime이 가장 작은 태스크를 우선적으로 선택하여 실행함으로써 모든 태스크에게 **공평한 CPU 점유율**을 보장하려 함. (Red-Black Tree 자료구조로 런큐 관리)
    *   **동작 흐름**:
        1.  타이머 인터럽트 발생 시 `scheduler_tick()` 호출 → 현재 태스크의 vruntime 갱신, 필요시 재스케줄링 플래그 설정.
        2.  인터럽트/시스템 콜 반환 직전, 재스케줄링 플래그 확인 후 `schedule()` 함수 호출.
        3.  `schedule()` -> `pick_next_task()`: CFS 로직에 따라 현재 코어의 런큐(RB-Tree)에서 vruntime이 가장 작은 다음 태스크 선택.
        4.  `context_switch()`: 스케줄링 준비. 이전 태스크(`prev`)와 다음 태스크(`next`)의 **메모리 관리 구조체(`mm_struct`) 주소를 비교**하여, 동일하면(같은 프로세스 내 스레드 전환) 페이지 테이블 관련 작업 생략. 통계 업데이트, 커널 훅 호출 등 수행.
        5.  `switch_to()`: 아키텍처 의존적인 저수준 함수(주로 어셈블리). 현재 스레드의 레지스터, 스택 포인터 등을 메모리(TCB)에 저장하고, 다음 스레드의 상태를 레지스터로 복원하며 실행 흐름 전환.
    *   **멀티코어 고려 사항**:
        *   **로드 밸런싱**: 특정 코어에 작업이 몰리지 않도록 주기적으로 또는 유휴 코어 발생 시 런큐 간 태스크를 이동시킴.
        *   **CPU 캐시 친화성(Cache Affinity)**: 스레드가 최근 실행되었던 코어에서 다시 실행될 가능성을 높여 캐시 히트율을 높임 (Warm cache). 로드 밸런싱과 상충될 수 있어 균형 필요.
        *   **NUMA(Non-Uniform Memory Access) 로컬리티**: 스레드가 사용하는 데이터가 물리적으로 가까운 메모리 노드에 위치한 코어에 스케줄링되도록 하여 메모리 접근 지연 시간 최소화.
        *   **SMT (Simultaneous Multi-Threading) / Hyper-Threading 인식**: OS는 물리 코어와 논리 코어(하이퍼스레드)를 구분하여 스케줄링. 같은 물리 코어의 하이퍼스레드들은 실행 유닛 일부를 공유하므로, 가능하다면 다른 물리 코어에 작업을 분산하려 함.
        *   **이종 멀티코어 (Heterogeneous Multi-Core, 예: ARM big.LITTLE)**: 성능 코어(big)와 효율 코어(LITTLE)를 구분하여, 작업의 특성(고성능 요구 vs 백그라운드)과 시스템 부하, 전력 상태에 따라 적절한 코어에 태스크 할당.

#### 1.7 CPU 아키텍처와 동시성 지원 메커니즘

CPU 코어 수의 한계와 더불어, 여러 코어가 효율적이고 정확하게 협력하기 위해서는 하드웨어 수준의 지원이 필수적이다.

*   **원자적 연산 (Atomic Operations)**:
    *   CPU 명령어 수준에서 중단 없이 한 번에 실행되는 연산. 예: Test-and-Set, Compare-and-Swap (CAS), Fetch-and-Add.
    *   이러한 연산들은 여러 코어가 공유 변수를 동시에 수정하려 할 때 발생하는 경쟁 상태를 막고 락(Lock)이나 Lock-Free 자료구조를 구현하는 데 핵심적인 역할을 한다. 컴파일러는 C++ `std::atomic`이나 Java `AtomicInteger` 같은 고수준 API를 통해 이러한 CPU 명령어를 활용한다.
*   **메모리 모델 (Memory Model)** 과 **메모리 장벽 (Memory Barriers/Fences)**:
    *   **메모리 모델**: CPU와 컴파일러가 메모리 연산(읽기, 쓰기)의 순서를 어떻게 재배치(reordering)할 수 있는지, 그리고 한 코어의 메모리 변경 사항이 다른 코어에 언제 어떻게 보이게 되는지(visibility)를 정의하는 규칙. 약한 메모리 모델(Weak Memory Model, 예: ARM)은 강한 메모리 모델(Strong Memory Model, 예: x86 일부)보다 더 많은 재배치를 허용하여 성능을 높이지만 프로그래머에게 더 많은 주의를 요구한다.
    *   **메모리 장벽**: 특정 지점에서 이전의 메모리 연산이 모두 완료되었음을 보장하거나, 이후의 연산이 먼저 실행되지 않도록 강제하는 CPU 명령어. 컴파일러 재배치와 CPU 재배치를 모두 제어한다. `volatile` 키워드(언어마다 의미 다름)나 명시적인 fence 명령(예: `mfence`, `atomic_thread_fence`)을 통해 사용. 동기화 프리미티브(락, 세마포어)의 정확한 동작을 위해 내부적으로 필수 사용된다.
*   **CPU 캐시 (CPU Cache) 와 캐시 일관성 (Cache Coherency)**:
    *   **CPU 캐시**: CPU 코어 내 또는 가까이 위치하는 작고 빠른 메모리. 자주 접근하는 데이터를 저장하여 메인 메모리 접근 지연을 줄인다. L1, L2, L3 캐시 등 계층 구조.
    *   **캐시 일관성**: 멀티코어 시스템에서 여러 코어가 각자의 캐시에 동일한 메모리 위치의 복사본을 가질 때, 이 복사본들이 일관된 값을 유지하도록 하는 메커니즘. 한 코어가 캐시된 데이터를 수정하면, 다른 코어들의 해당 데이터 캐시 라인은 무효화되거나 업데이트되어야 한다. **MESI (Modified, Exclusive, Shared, Invalid)** 또는 MOESI 등의 프로토콜이 사용된다. 이 과정에서 코어 간 통신(버스 트래픽)이 발생하며, 동시성 프로그램의 성능에 큰 영향을 미친다.
*   **거짓 공유 (False Sharing)**:
    *   서로 다른 스레드에서 접근하는 독립적인 데이터들이 우연히 동일한 캐시 라인(Cache Line, 예: 64 바이트)에 위치할 때 발생. 한 스레드가 자신의 데이터를 수정하면, 해당 캐시 라인 전체가 다른 코어에서 무효화된다. 이로 인해 다른 스레드는 실제로는 변경되지 않은 자신의 데이터를 다시 메인 메모리에서 읽어와야 하는 불필요한 캐시 미스와 성능 저하를 겪는다. 데이터 구조를 패딩(padding)하여 의도적으로 다른 캐시 라인에 배치함으로써 회피할 수 있다.
*   **SMT (Simultaneous Multi-Threading) / Hyper-Threading**:
    *   하나의 물리적 CPU 코어가 여러 개의 논리적 코어(하드웨어 스레드)로 보이도록 하는 기술. 각 논리 코어는 자신만의 레지스터 상태를 가지지만, 실행 유닛(ALU, FPU 등)이나 캐시 등은 공유한다. OS는 이를 별개의 코어로 인식하고 스레드를 스케줄링한다. I/O 대기 등으로 한 논리 코어가 유휴 상태일 때 다른 논리 코어가 공유 자원을 활용하여 전체적인 코어 활용률을 높일 수 있지만, 두 논리 코어가 동시에 자원 경합을 벌이면 물리 코어 하나만 사용하는 것보다 성능이 떨어질 수도 있다.

### 2. 동시성 제어: 락(Lock)과 동기화

#### 2.1 동기화의 필요성: 경쟁 상태와 스레드 안전성

여러 스레드가 **공유 자원**(특히 변경 가능한 데이터)에 동시에 접근하여 읽거나 쓸 때, 특히 **멀티 코어 환경에서 병렬적으로 실행될 때**, 스레드 실행 순서(컴파일러 최적화, CPU의 비순차적 실행, 캐시 효과 등으로 인해 예측 불가능)에 따라 결과가 달라지거나 의도치 않은 상태가 되는 문제를 **경쟁 상태(Race Condition)**라고 합니다. 이로 인해 데이터가 깨지거나(Data Inconsistency) 프로그램 오작동이 발생할 수 있습니다. 락(Lock), 세마포어 등의 동기화 메커니즘은 임계 구역(Critical Section)을 보호하여 한 번에 하나의 스레드(또는 정해진 수의 스레드)만 접근하도록 제어함으로써 경쟁 상태를 방지하고 코드의 **스레드 안전성(Thread Safety)**을 확보하는 데 사용됩니다. 이는 결국 제한된 CPU 코어 위에서 여러 스레드가 질서 있게 공유 자원을 사용하도록 강제하는 것입니다.

#### 2.2 기본 동기화 프리미티브

*   **뮤텍스 (Mutex - Mutual Exclusion)**: 임계 구역에 오직 **하나**의 스레드만 진입하도록 보장. `lock()` (획득 시도, 실패 시 대기) / `unlock()` (해제) 연산 제공. 가장 기본적이고 널리 쓰임. 락 획득 실패 시 스레드는 일반적으로 OS에 의해 대기 상태(Blocked)로 전환되어 CPU 자원을 소모하지 않는다.
*   **세마포어 (Semaphore)**: 지정된 개수(N)만큼의 스레드가 동시에 특정 자원에 접근하거나 임계 구역을 실행하도록 허용. 내부적으로 **정수 카운터**를 가짐. `wait()` (또는 P) 연산은 카운터를 감소시키려 시도 (카운터가 0이면 양수가 될 때까지 대기), `signal()` (또는 V) 연산은 카운터를 증가시키고 대기 중인 스레드를 깨움. N=1이면 **바이너리 세마포어**(뮤텍스와 유사하게 동작하나, 소유권 개념이 없을 수 있음).
*   **스핀락 (Spinlock)**: 락을 얻을 수 있을 때까지 **CPU를 사용하며 계속 확인**(busy-waiting)하는 방식. 락을 얻기 위해 `while(try_lock() == false) { cpu_relax(); }` 와 같은 루프를 실행.
    *   **장점**: 컨텍스트 스위치 오버헤드가 없어 임계 구역이 매우 짧고 락 보유 시간이 짧을 것으로 예상될 때 뮤텍스보다 빠를 수 있다. 특히 멀티 코어 환경에서 다른 코어가 곧 락을 해제할 가능성이 있을 때 유용.
    *   **단점**: 락 경합이 심하거나 대기 시간이 길어지면 CPU 자원을 심하게 낭비 (한 코어가 계속 루프를 돌며 다른 유용한 작업을 못함). 싱글 코어 환경에서는 스핀락을 사용하는 스레드가 CPU를 점유하고 있으면 락을 가진 다른 스레드가 실행될 기회를 얻지 못해 거의 항상 비효율적 (선점형 스케줄러가 개입하지 않는 한).
    *   **`cpu_relax()`**: 스핀 루프 내에서 호출되는 저수준 명령어(예: x86의 `PAUSE`, ARM의 `YIELD`). CPU 파이프라인을 비우거나 전력 소모를 약간 줄이고, SMT 환경에서는 같은 물리 코어의 다른 하이퍼스레드에게 실행 기회를 더 줄 수 있음.
    *   **사용처**: 주로 OS 커널 내부의 매우 짧은 데이터 구조 보호, 인터럽트 핸들러 등 컨텍스트 스위치가 불가능하거나 매우 비싼 환경. 사용자 공간에서는 신중하게 사용해야 하며, **적응형 뮤텍스(Adaptive Mutex)**는 초기에는 스핀하다가 일정 시간 후 블록킹으로 전환하는 하이브리드 방식.

#### 2.3 조건 변수 (Condition Variables)

*   **역할**: 뮤텍스/락과 함께 사용되어, 특정 **조건(Predicate)**이 만족될 때까지 스레드가 **락을 잠시 풀고 효율적으로 대기**하도록 돕는 메커니즘. busy-waiting을 피하고 CPU 자원을 절약.
*   **동작**:
    1.  스레드는 **락을 먼저 획득**한 후, 보호된 공유 변수를 검사하여 조건 충족 여부 확인.
    2.  조건이 만족되지 않으면, 해당 조건 변수에 대해 `wait()` (또는 `await()`) 호출. 이 호출은 **원자적으로** 다음 작업을 수행:
        *   스레드를 조건 변수의 대기 큐에 등록.
        *   **획득했던 락을 해제**. (다른 스레드가 락을 획득하여 조건을 변경할 수 있도록)
        *   스레드를 WAITING 상태로 전환 (블록되어 CPU 사용 안 함).
    3.  다른 스레드가 락을 획득하고 공유 변수를 수정하여 **조건을 만족**시키게 되면, 해당 조건 변수에 대해 `signal()` (또는 `notify()`) / `signalAll()` (또는 `notifyAll()`) 호출.
    4.  `signal/notify`는 대기 중인 스레드 중 **하나**(또는 전부)를 깨움(unblock). 깨어난 스레드는 스케줄러에 의해 실행 가능 상태(Runnable)가 됨.
    5.  깨어난 스레드는 `wait()` 호출 지점부터 다시 실행을 시작하며, **자동으로 락을 다시 획득**하려고 시도함. (락 획득 후)
    6.  (Spurious wakeup - 허위 각성: 조건이 만족되지 않았음에도 `wait`에서 깨어나는 현상. OS 구현상의 이유나 경쟁 상태 회피 목적으로 발생 가능) 가능성 때문에 **반드시 루프 안에서 조건을 다시 확인**해야 함. `while (!condition) { cond_var.wait(); }` 형태 권장.
*   **예**: Java의 `Object.wait/notify/notifyAll` (객체의 고유 락과 연동), `java.util.concurrent.locks.Condition` (ReentrantLock 등과 연동).

#### 2.4 교착 상태 (Deadlock)

*   **정의**: 두 개 이상의 스레드(또는 프로세스)가 서로 상대방이 점유하고 있는 자원을 해제하기를 기다리며 무한정 대기하는 상태. 프로그램이 더 이상 진행되지 못하고 CPU는 유휴 상태가 되거나 다른 작업만 처리하게 됨.
*   **발생 조건** (Coffman 조건 - 4가지 모두 충족 시):
    1.  **상호 배제 (Mutual Exclusion)**: 자원은 한 번에 하나의 스레드만 사용할 수 있음 (락).
    2.  **점유 대기 (Hold and Wait)**: 스레드가 최소한 하나의 자원을 보유한 상태에서, 다른 스레드가 보유한 자원을 추가로 기다림.
    3.  **비선점 (No Preemption)**: 다른 스레드가 사용 중인 자원을 강제로 빼앗을 수 없음. 자원은 보유한 스레드가 자발적으로 해제해야 함.
    4.  **순환 대기 (Circular Wait)**: 스레드들이 순환 형태로 다음 스레드가 요구하는 자원을 보유하고 있음 (예: T1 -> T2가 가진 자원 요구, T2 -> T1이 가진 자원 요구).
*   **해결 전략**:
    *   **예방 (Prevention)**: 4가지 조건 중 하나 이상을 깨뜨리도록 시스템 설계. (예: 모든 락 획득 순서 강제, 자원 필요시 한꺼번에 요청, 타임아웃 사용, `tryLock` 사용).
    *   **회피 (Avoidance)**: 시스템 상태를 계속 감시하며 교착 상태 가능성이 있는 자원 할당 요청을 거부 (예: 은행원 알고리즘). 실행 시 자원 요구량 정보를 미리 알아야 해서 일반 OS에서는 잘 사용되지 않음.
    *   **탐지 및 복구 (Detection & Recovery)**: 주기적으로 자원 할당 그래프 등을 통해 교착 상태 발생 여부 탐지. 발생 시 교착 상태에 빠진 스레드 중 일부를 강제 종료하거나, 자원을 선점하여 복구 (롤백 필요).
    *   **무시 (Ignorance)**: 교착 상태 발생 빈도가 매우 낮다고 가정하고 특별한 조치를 취하지 않음 (일반적인 OS 접근 방식). 개발자가 주의 깊게 설계하고 테스트하여 방지해야 함.

#### 2.5 우선순위 역전 (Priority Inversion) 및 해결책

*   **문제 상황**: 낮은 우선순위 스레드(L)가 락(뮤텍스)을 보유 중인데, 높은 우선순위 스레드(H)가 이 락을 기다리며 블록됨. 이때 L보다 우선순위가 높지만 H보다는 낮은 중간 우선순위 스레드(M)가 CPU를 할당받아 실행되면, H는 M 때문에 실행 기회를 얻지 못하는 L을 무한정 기다리게 되는 현상. 중요한 작업(H)이 CPU 자원을 할당받지 못해 시스템 응답성 저하 또는 데드라인 미스 초래. 실시간 시스템 등에서 심각한 문제 유발 가능.
*   **원인**: 락 자체의 문제가 아니라, OS 스케줄러가 우선순위 기반으로 RUNNABLE 상태의 스레드(M, L)만 고려하기 때문. H는 BLOCKED 상태라 스케줄링 대상에서 제외됨.
*   **해결책**:
    *   **우선순위 상속 (Priority Inheritance Protocol - PIP)**: H가 L이 가진 락을 기다리기 시작하면, 커널이 L의 실행 우선순위를 일시적으로 H의 우선순위와 같거나 높게 **상속(inherit)**시켜 줌. 이로써 L이 M보다 먼저 CPU를 얻어 락을 빨리 해제하도록 유도. L이 락을 해제하면 원래 우선순위로 복귀.
    *   **우선순위 보호/상한 (Priority Ceiling Protocol - PCP)**: 각 공유 자원(락)에 미리 접근 가능한 스레드의 최대 우선순위(priority ceiling)를 지정해 둠. 어떤 스레드든 해당 락을 획득하는 순간, 자신의 실행 우선순위를 즉시 그 ceiling 값으로 **승격(promote)**시킴. 락 해제 시 원래 우선순위로 복귀. 락 획득 조건 자체에 ceiling 관련 검사를 포함하여(현재 실행 중인 어떤 스레드도 자신이 획득하려는 락의 ceiling보다 높은 우선순위를 가지면서 다른 락을 점유하고 있지 않아야 함) 우선순위 역전 및 연쇄적인 블로킹, 교착 상태를 원천적으로 방지. PIP보다 예측 가능성이 높으나 설계가 복잡할 수 있음.
*   **구현**: POSIX `pthread_mutexattr_setprotocol` 함수로 뮤텍스 속성(`PTHREAD_PRIO_INHERIT`, `PTHREAD_PRIO_PROTECT`) 설정 가능. 주로 실시간 운영체제(RTOS)나 실시간 스케줄링 정책(Linux의 `SCHED_FIFO`, `SCHED_RR`) 하에서 유효하게 동작함. Java 표준 스케줄러에는 해당 프로토콜이 내장되어 있지 않아, Java 레벨에서는 우선순위 역전 문제에 더 취약할 수 있으며, `ReentrantLock` 등을 사용할 때 주의 필요.

#### 2.6 Lock-Free 프로그래밍과 Non-Blocking 알고리즘

CPU 코어 수 증가에 따른 확장성(Scalability)을 극대화하고, 락으로 인한 문제점(교착 상태, 우선순위 역전, 성능 병목)을 피하기 위한 고급 기법.

*   **정의**: 락을 사용하지 않고 여러 스레드가 공유 데이터에 안전하게 접근하도록 설계된 알고리즘 및 자료구조.
*   **기반 기술**: CPU가 제공하는 **원자적 연산(CAS 등)**과 **메모리 장벽**을 정교하게 활용.
*   **종류**:
    *   **Wait-Free**: 모든 스레드가 항상 유한한 단계 내에 자신의 연산을 완료함을 보장. 다른 스레드의 속도나 중단에 영향을 받지 않음. 가장 강력하지만 구현이 매우 어려움.
    *   **Lock-Free**: 시스템 전체적으로 최소한 하나의 스레드는 항상 진행 중임을 보장. 특정 스레드가 기아(starvation) 상태에 빠질 수는 있음. (예: CAS 루프에서 계속 실패하는 스레드)
    *   **Obstruction-Free**: 한 스레드가 다른 스레드와의 경합 없이 단독으로 실행될 경우 유한 단계 내에 연산을 완료함을 보장. 경합이 있으면 롤백하고 재시도할 수 있음.
*   **장점**:
    *   교착 상태 및 우선순위 역전 문제 원천 방지.
    *   락 경합으로 인한 컨텍스트 스위칭이나 스핀 대기 비용 감소 가능성 (특히 코어 수가 많을 때).
    *   일부 스레드 장애에 더 강인할 수 있음 (락을 가진 스레드가 죽는 문제 없음).
    *   신호 처리기나 인터럽트 핸들러 내에서 안전하게 사용 가능.
*   **단점**:
    *   설계 및 구현이 매우 복잡하고 어려움. 미묘한 버그(ABA 문제 등) 발생 가능성.
    *   모든 문제에 적용하기 어려움. 특정 자료구조(큐, 스택, 리스트 등)에 대한 연구 활발.
    *   경합이 적은 상황에서는 오히려 락 기반 구현보다 성능이 낮을 수 있음 (CAS 루프 오버헤드).
    *   메모리 소비량이 더 클 수 있음 (예: 노드 복사).
*   **ABA 문제**: CAS 연산 시 발생하는 문제. A 값을 가진 메모리 위치를 읽고, B로 바꾸려 할 때, 그 사이에 다른 스레드가 값을 A에서 C로, 다시 A로 변경했다면 CAS는 성공하지만 논리적으로는 오류일 수 있음. 버전 번호(태그)를 함께 사용하여 회피.
*   **예시**: Java의 `java.util.concurrent.atomic` 패키지 (`AtomicInteger`, `AtomicReference`), `ConcurrentLinkedQueue`, `ConcurrentSkipListMap`.

### 3. 구체적인 구현: POSIX, Java, C

#### 3.1 POSIX/glibc 락 구현 상세

*   **저수준 기반 기술**:
    *   **원자적 연산 (Atomic Operations)**: `__atomic_compare_exchange_n`, `__atomic_fetch_add`, `__atomic_exchange_n` 등 컴파일러 내장 함수 또는 아키텍처별 어셈블리 명령어를 사용하여 메모리 값을 원자적으로 읽고 수정. 락 상태 변경 등에 사용. (이는 CPU의 직접적인 지원임)
    *   **futex (Fast Userspace Mutex)**: Linux 커널이 제공하는 시스템 콜. 사용자 공간에서 원자적 연산으로 락 획득/해제를 시도하고, **경합이 발생했을 때만** 커널 모드로 전환하여 스레드를 효율적으로 대기/깨우는 메커니즘. `FUTEX_WAIT` (대기), `FUTEX_WAKE` (깨우기) 연산 제공. 대부분의 POSIX 동기화 프리미티브가 내부적으로 futex를 사용. 커널 개입을 최소화하여 성능 향상.
*   **`pthread_mutex_t` (뮤텍스)**:
    *   **비경합 경로 (Fast Path)**: 락 변수(내부 필드, 보통 정수)가 0(unlocked)일 때, CPU의 원자적 연산(예: CAS 또는 atomic exchange)으로 1(locked)로 바꾸고 즉시 리턴. 커널 호출 없음.
    *   **경합 경로 (Contention Path)**: 원자적 연산 실패 시, (뮤텍스 타입이나 시스템 설정에 따라) 짧은 시간 동안 **스핀(adaptive spinning)**하며 락이 해제되기를 기다릴 수 있음. 이는 멀티 코어 환경에서 다른 코어가 락을 곧 해제할 것이라는 기대 하에 컨텍스트 스위치 비용을 절약하려는 시도. 계속 실패하면 `futex(FUTEX_WAIT_PRIVATE, ...)`를 호출하여 커널의 대기 큐에 등록되고 스레드는 블록됨 (WAITING 상태).
    *   **Unlock**: 락 변수를 0으로 바꾸고(원자적 연산 사용), `futex(FUTEX_WAKE_PRIVATE, ...)`를 호출하여 대기 중인 스레드 하나(또는 그 이상, 정책에 따라)를 깨움.
    *   **부가 기능**: 재진입(`PTHREAD_MUTEX_RECURSIVE`), 에러 체크(`PTHREAD_MUTEX_ERRORCHECK`), 우선순위 제어(`PTHREAD_PRIO_INHERIT`/`PROTECT` - PIP/PCP 프로토콜 사용), 로버스트(`PTHREAD_MUTEX_ROBUST` - 락 소유 스레드 사망 시 다른 스레드가 락을 복구하고 일관성을 유지할 수 있도록 함).
*   **`sem_t` (세마포어)**:
    *   `sem_wait()`: 내부 카운터 값을 원자적으로 감소 시도(`__atomic_fetch_sub` 등). 결과가 0 이상이면 성공. 음수(또는 0이 되기 전)가 되면 `futex(FUTEX_WAIT...)`로 블록.
    *   `sem_post()`: 내부 카운터 값을 원자적으로 증가(`__atomic_fetch_add` 등). 증가 후 값이 특정 조건(예: 0에서 1이 되거나, 대기자가 있음을 나타내는 플래그 확인)을 만족하면, `futex(FUTEX_WAKE...)`로 대기 중인 스레드 하나를 깨움.
    *   **부가 기능**: 프로세스 간 공유(`pshared` 플래그 설정 시 공유 메모리에 세마포어 생성 가능), 타임아웃 대기(`sem_timedwait`).
*   **`pthread_spinlock_t` (스핀락)**:
    *   `lock()`: `__atomic_exchange_n` 또는 `__atomic_test_and_set` 같은 CPU 원자적 명령어로 락 변수를 1(locked)로 설정 시도. 성공할 때까지 루프를 돌며 `CPU_PAUSE` 또는 `__builtin_ia32_pause()` (x86), `asm volatile("yield")` (ARM) 등과 같은 **`cpu_relax()`** 매크로를 호출. 이는 CPU 파이프라인을 비우고, 전력 소모를 줄이며, SMT 환경에서 다른 하이퍼스레드에게 기회를 줄 수 있음. **futex 사용 안 함**. 순수 사용자 공간에서 busy-waiting.
    *   `unlock()`: 락 변수를 원자적으로 0(unlocked)으로 설정 (`__atomic_clear` 또는 `__atomic_store_n`).
    *   **부가 기능**: 없음. 매우 짧은 임계 구역 전용. 커널 내부에서 더 많이 사용.
*   **`pthread_rwlock_t` (Reader-Writer Lock)**:
    *   내부적으로 하나의 정수(state word)에 리더 수, 라이터 존재 여부(쓰기 락 플래그), 쓰기 락 대기자 존재 여부, 리더 락 대기자 존재 여부 등을 비트 필드로 효율적으로 관리.
    *   `rdlock()`: 라이터가 없고, (정책에 따라) 쓰기 락 대기자가 없을 때 상태 변경에 성공하면(리더 수 원자적 증가) 즉시 리턴. 실패 시 futex를 이용해 대기. Writer-preference 또는 Reader-preference 정책 가능.
    *   `wrlock()`: 리더와 라이터가 모두 없을 때 CAS 등으로 상태 변경 시도(쓰기 락 플래그 설정). 실패 시 futex 대기.
    *   `unlock()`: 상태 복원 후 `futex(FUTEX_WAKE)`로 대기 중인 리더들(다수 가능) 또는 라이터(하나)를 적절히 깨움. 구현이 복잡하며, 기아 문제 발생 가능성 있음.

#### 3.2 Java 락 구현 상세

Java의 락은 JVM 내부에서 OS의 동기화 프리미티브(예: futex, Windows CriticalSection/Events)와 CPU의 원자적 연산을 조합하여 구현됨.

*   **저수준 기반 기술**:
    *   **`sun.misc.Unsafe` / `java.lang.invoke.VarHandle` (Java 9+)**: CAS(Compare-And-Swap), volatile 읽기/쓰기, 메모리 장벽(fences) 등 저수준 메모리 연산 제공. JVM 내부 및 `java.util.concurrent` (j.u.c) 패키지에서 광범위하게 사용됨. CPU의 원자적 명령어와 메모리 모델을 직접 활용.
    *   **`java.util.concurrent.locks.LockSupport`**: 스레드를 블록(`park()`, `parkNanos()`, `parkUntil()`)시키거나 깨우는(`unpark(Thread)`) 저수준 기능 제공. 내부적으로 OS의 스레드 블록/깨우기 메커니즘(예: Linux futex, Windows WaitObject/Events, macOS `os_unfair_lock_cond_wait/signal`) 사용. 스레드 상태를 WAITING/TIMED_WAITING으로 변경.
    *   **`AbstractQueuedSynchronizer (AQS)`**: `java.util.concurrent`의 대부분 락 구현(ReentrantLock, Semaphore, CountDownLatch 등)의 핵심 프레임워크.
        *   **`state` 변수**: `volatile int` 또는 `long`. 락의 상태(예: 락 보유 여부, 재진입 횟수, 남은 permit 수)를 나타냄. `Unsafe` 또는 `VarHandle`을 통한 CAS로 원자적 변경. `volatile` 키워드로 가시성 보장.
        *   **CLH 대기 큐 (Node)**: 락 획득 실패 시 스레드를 담는 노드(Node)를 FIFO 기반의 양방향 연결 리스트(CLH 큐 변형)에 삽입. 각 노드는 대기 중인 스레드, 이전/다음 노드 포인터, 대기 상태(`waitStatus` - SIGNAL, CANCELLED, CONDITION 등) 정보 포함.
        *   **`acquire()` 템플릿 메서드**:
            1.  `tryAcquire()` (상속받아 구현) 호출 -> 성공 시 리턴.
            2.  실패 시 `addWaiter()`로 현재 스레드를 큐의 꼬리에 노드로 추가.
            3.  `acquireQueued()` 루프 진입:
                *   자신의 노드가 헤드 바로 다음이고(`isFirst()`) `tryAcquire()` 성공할 때까지 반복.
                *   성공하면 자신을 헤드로 만들고 리턴.
                *   실패하면 `shouldParkAfterFailedAcquire()`로 이전 노드의 `waitStatus`를 SIGNAL로 설정하고, `parkAndCheckInterrupt()` (`LockSupport.park()`) 호출하여 현재 스레드 대기.
        *   **`release()` 템플릿 메서드**:
            1.  `tryRelease()` (상속받아 구현) 호출 -> 성공 시
            2.  `unparkSuccessor()` (`LockSupport.unpark()`) 호출하여 큐의 다음 유효한 노드(헤드의 다음 노드)에 있는 스레드를 깨움.
        *   (공유 락(`acquireShared`/`releaseShared`)은 유사하지만 여러 스레드가 동시에 락을 획득할 수 있도록 다른 로직 사용). AQS는 CPU 코어에 의존적인 스핀을 짧게 시도하기도 전에(또는 후에) `LockSupport.park()`를 호출하여 스레드를 대기시킨다.

*   **`synchronized` (JVM 모니터 락)**:
    *   **분류**: 뮤텍스, 재진입 가능(Reentrant). 각 Java 객체는 고유한 모니터(Monitor)를 가질 수 있다.
    *   **구현**: 각 Java 객체는 내부적으로 **모니터(Monitor)**를 가짐. 모니터는 객체 헤더의 **Mark Word**(몇 바이트)와 연결됨. 락 획득 시 Mark Word 상태 변경. JVM은 성능 최적화를 위해 락 상태가 단계적으로 변화(Lock Escalation)하도록 설계. 이는 CPU 코어 수 및 경합 상황에 따라 효율성을 높이기 위함:
        1.  **Bias Locking (편향 잠금)** (기본적으로 비활성화되는 추세, JDK 15+): 첫 스레드가 락 획득 시 Mark Word에 스레드 ID 기록. 이후 같은 스레드가 재진입 시 CAS 없이 Mark Word의 스레드 ID만 확인하고 바로 락 획득 (매우 빠름). 다른 스레드가 락 요청 시 또는 특정 조건(세이프포인트)에서 편향 해제(revoke) 후 경량 잠금으로 전환.
        2.  **Lightweight Locking (경량 잠금)**: 여러 스레드가 번갈아 가며 락 획득 시 사용. 스레드 스택 프레임에 **Lock Record** 생성 후, CAS를 이용해 객체 Mark Word와 Lock Record 주소를 교환(swap) 시도. 성공 시 락 획득. 실패(경합 발생) 시 짧은 시간 동안 **스핀(Spin-locking)**하며 락이 해제되기를 기다릴 수 있음(Adaptive Spinning). 스핀 실패 시 중량 잠금으로 확장.
        3.  **Heavyweight Locking (중량 잠금)**: 여러 스레드가 동시에 락을 경합하여 경량 잠금으로 처리할 수 없는 경우. 객체에 연결된 실제 OS 수준의 **ObjectMonitor** 생성(또는 재사용). 이 ObjectMonitor는 내부적으로 OS 뮤텍스(예: futex)와 조건 변수를 사용. 스레드는 ObjectMonitor의 대기 큐(`cxq`, `EntryList`)에 등록되고, OS 수준의 동기화 메커니즘(**futex** 등)을 통해 **`LockSupport.park()`** 되어 블록됨 (WAITING/BLOCKED 상태).
    *   **Unlock**: 역순으로 상태 변경 시도. Heavyweight 락 해제 시 대기 큐의 스레드를 **`LockSupport.unpark()`**로 깨움.
    *   **부가 기능**: `Object.wait()`, `notify()`, `notifyAll()` 메서드는 모니터의 **Wait Set**과 연동되어 조건 변수 역할 수행 (락 임시 해제 및 대기/깨우기). 이들 역시 ObjectMonitor를 통해 구현.

*   **`ReentrantLock`**:
    *   **분류**: 뮤텍스, 재진입 가능. `synchronized`보다 유연하고 다양한 기능 제공.
    *   **구현**: AQS 기반. `state`는 락 보유 스레드의 재진입 횟수 (0이면 unlocked). `tryAcquire`는 현재 스레드가 소유자인지 확인, CAS로 `state` 변경 시도.
    *   **부가 기능**: **공정성(Fairness)** 선택 가능 (Fair: AQS 큐 순서대로, Unfair: 새 요청이 끼어들기 가능 - 일반적으로 성능 유리), **타임아웃/인터럽트** 가능한 락 획득(`tryLock`, `lockInterruptibly`), **`Condition`** 객체 생성 가능(AQS의 `ConditionObject` 사용, 여러 조건 변수 가능).

*   **`Semaphore`**:
    *   **분류**: 세마포어.
    *   **구현**: AQS 기반. `state`는 사용 가능한 허가(permit) 개수. `acquire` (`tryAcquireShared`)는 CAS로 `state` 감소 시도. `release` (`tryReleaseShared`)는 `state` 증가 후 대기 스레드 `unpark`.
    *   **부가 기능**: 공정성 선택, 타임아웃/인터럽트 가능 acquire.

*   **`ReentrantReadWriteLock`**:
    *   **분류**: Reader-Writer 락. 읽기 작업은 공유 가능, 쓰기 작업은 배타적.
    *   **구현**: AQS 기반. `state`를 32비트 정수로 사용하여 상위 16비트는 읽기 락 횟수(공유 모드), 하위 16비트는 쓰기 락 횟수(배타 모드, 재진입 포함) 관리. 읽기 락은 공유(shared), 쓰기 락은 배타적(exclusive) 모드로 AQS 사용.
    *   **부가 기능**: 재진입(Writer는 읽기/쓰기 모두, Reader는 읽기만), **락 다운그레이드**(Write 락 보유 중 Read 락 획득 가능 후 Write 락 해제), **락 업그레이드 불가**(Read 락 보유 중 Write 락 획득 시도 시 교착상태 방지를 위해 일반적으로 허용 안됨, 해제 후 다시 획득), 공정성 선택, 쓰기 락에 대한 `Condition`.

*   **`StampedLock`** (Java 8+):
    *   **분류**: Optimistic Read + Reader-Writer 락. `ReentrantReadWriteLock`보다 복잡하지만 특정 상황에서 더 높은 처리량 목표. 비관적 락보다 성능 향상 목표.
    *   **구현**: AQS 미사용. 64비트 `long` 타입 `state` (스탬프 값)를 직접 CAS로 관리. 스탬프에는 락 모드(읽기/쓰기/낙관적 읽기) 및 버전(또는 시퀀스) 정보 포함.
    *   **Optimistic Read**: `tryOptimisticRead()`로 스탬프(0이 아닌 값)를 얻음 (락 획득 아님, 매우 빠름) -> 공유 데이터 읽음 -> `validate(stamp)`로 읽는 동안 쓰기 락 발생(스탬프 변경) 여부 확인. 유효하면(변경 없음) 락 없이 읽기 성공. 실패 시 일반 읽기 락(`readLock()`) 획득 시도.
    *   **Read/Write Lock**: CAS 기반 획득 시도, 실패 시 내부 대기 큐(간단한 Treiber 스택 유사 구조)와 `LockSupport.park/unpark` 사용.
    *   **부가 기능**: 낙관적 읽기, 락 모드 변환 시도(`tryConvertToWriteLock` 등). **재진입 불가**, 인터럽트 처리 방식이 다름(메서드 이름에 명시), `Condition` 미지원. 사용 시 주의 필요하며, 매우 특수한 고성능 시나리오에 적합.

*   **(락 대기 중 스레드 상태)**: AQS 기반 락, `synchronized` 헤비웨이트 락 대기 시 스레드는 **WAITING/BLOCKED** 상태가 되어 OS **런큐에서 제외**됨. `LockSupport.park` 호출. 이는 CPU 코어를 불필요하게 점유하지 않기 위함. 스핀락 또는 `synchronized`의 경량 잠금 단계에서의 스핀은 **RUNNABLE** 상태 유지.

### 4. 최신 동시성 모델: 가상 스레드와 코루틴

#### 4.1 등장 배경: OS 스레드의 한계

OS 커널 스레드(KLT)는 강력하지만, 다음과 같은 한계로 인해 특히 "요청당 스레드(Thread-Per-Request)" 모델을 사용하는 I/O 바운드 애플리케이션에서 CPU 코어 활용률 저하 및 확장성 문제를 야기합니다:

1.  **생성 및 컨텍스트 스위칭 비용**: KLT 생성 시 커널 자료구조 할당, 스택 공간 할당 등 오버헤드가 있으며, 컨텍스트 스위칭 시에도 커널 모드 전환, 레지스터 저장/복원 등 비용 발생. CPU 코어가 많아도 스레드가 너무 많으면 이 오버헤드가 성능을 잠식.
2.  **메모리 소모**: 각 KLT는 커널 자원 외에도 독립적인 스택 메모리(보통 수백 KB ~ 수 MB)를 소모. 동시 사용자 수가 많은 시스템(수만~수십만)에서는 수많은 스레드가 필요하며, 이는 막대한 메모리 점유로 이어져 시스템이 지원 가능한 총 스레드 수를 제한. 이는 가용 RAM에 의해 간접적으로 CPU 코어 당 효과적으로 운영할 수 있는 OS 스레드 수를 제한한다.
3.  **I/O 대기 시 CPU 낭비 (간접적)**: I/O 작업(네트워크, 디스크)은 CPU 속도에 비해 매우 느림. KLT가 I/O를 기다리며 블록되면 해당 스레드는 CPU를 사용하지 않지만, 스택 메모리와 커널 자원은 계속 점유. OS 스케줄러는 다른 스레드를 실행시키지만, 많은 스레드가 블록 상태에 있으면 활성 스레드 수가 적어 CPU 코어들이 충분히 활용되지 못할 수 있고, 컨텍스트 스위칭만 빈번해질 수 있음.

이러한 한계는 CPU 코어 수 자체의 한계라기보다는, **제한된 CPU 코어를 효율적으로 사용하기 위한 OS 스레드 모델의 비용 문제**입니다. 가상 스레드와 코루틴은 적은 수의 OS 스레드(플랫폼 스레드)를 사용하여 수많은 동시 작업을 처리함으로써 이러한 문제를 해결하려 합니다.

#### 4.2 Java 가상 스레드 (Virtual Threads - Project Loom, Java 19+ 정식 기능)

*   **개념**: OS 스레드(플랫폼 스레드)에 직접 매핑되지 않고 **JVM이 관리**하는 매우 가벼운 **사용자 수준 스레드**. 기존 `java.lang.Thread` API와 거의 호환됨.
*   **실행 모델**: 기본적으로 JVM이 제공하는 공유 **ForkJoinPool** (또는 커스텀 ExecutorService)을 **캐리어 스레드 풀(Carrier Thread Pool)**로 사용. 이 풀의 플랫폼 스레드(OS 스레드) 위에서 가상 스레드가 실행됨. 하나의 캐리어 스레드가 여러 가상 스레드를 시분할 방식으로 번갈아 실행 가능 (M:N 매핑). 캐리어 스레드 수는 보통 CPU 코어 수와 비슷하게 유지됨.
*   **블로킹 처리 (핵심)**: 가상 스레드가 **JDK 내에서 인지 가능한 블로킹 작업**(대부분의 `java.net` I/O, `Thread.sleep`, `BlockingQueue.take`, `Lock.lock()` (j.u.c 락들), `synchronized` 블록/메서드 경합 등)을 만나면:
    1.  가상 스레드의 실행 상태(특히 **스택**)를 힙 메모리에 있는 **Continuation** 객체에 저장 (스택 스필 - Stack Spill, 또는 "마운트 해제 - unmount").
    2.  가상 스레드는 **주차(park)** 상태가 됨 (WAITING). JVM 스케줄러에 의해 관리.
    3.  해당 가상 스레드를 실행하던 **캐리어 스레드(플랫폼 스레드)는 즉시 풀로 반환**되어 다른 준비된 가상 스레드나 작업을 실행할 수 있게 됨. (OS 스레드가 블록되지 않음!)
    4.  블로킹 작업이 완료되면(예: 네트워크 응답 도착, 락 해제), JVM 스케줄러가 해당 가상 스레드를 **해제(unpark)**하고, 가용한 캐리어 스레드에 할당("마운트 - mount")하여 Continuation에서 스택 상태를 복원(리스토어)하고 중단된 지점부터 실행 재개. (다른 캐리어 스레드에서 재개될 수 있음)
*   **스택 관리**: 가상 스레드는 필요에 따라 크기가 조절되는 스택을 가짐 (힙 메모리 일부를 스택처럼 사용 가능). 전체 호출 스택 정보를 보존하여 기존 디버깅/프로파일링 도구와 호환성 유지.
*   **장점**:
    *   **경량성**: 생성/소멸 비용 매우 저렴, 메모리 사용량 적음(플랫폼 스레드 대비 수백 바이트~수 킬로바이트 수준). 수백만 개 동시 생성/관리 가능.
    *   **높은 처리량**: I/O 바운드 작업에서 플랫폼 스레드가 블록되지 않고 계속 다른 가상 스레드를 처리하므로 시스템 전체 처리량 크게 향상. CPU 코어 활용률 극대화.
    *   **호환성**: 기존 `Thread` API 및 블로킹 I/O 라이브러리(JDBC, 서블릿 API 등) 코드 변경 거의 없이 그대로 사용 가능 (Drop-in replacement).
    *   **개발 용이성**: 동기식/절차적 코드 스타일 유지 가능. 콜백 헬(Callback Hell)이나 복잡한 비동기 API(CompletableFuture, RxJava 등) 학습 부담 적음.
    *   **도구 지원**: 기존 디버깅, 프로파일링, 모니터링 도구(JFR, JMX 등) 그대로 사용 가능.
*   **단점 및 주의사항**:
    *   코루틴보다는 메모리 오버헤드가 클 수 있음 (전체 스택 복사 및 관리).
    *   **Pinning**: 가상 스레드가 `synchronized` 블록/메서드 내에서 블록되거나, 네이티브 JNI 호출 중 블록될 경우, 해당 가상 스레드는 캐리어 스레드에서 분리(unmount)되지 못하고 캐리어 스레드를 점유한 채로 블록됨 (pinning). 이 경우 해당 캐리어 스레드는 다른 가상 스레드를 실행할 수 없게 되어 성능 저하 유발 가능. JDK는 `synchronized`에 의한 pinning을 줄이기 위해 노력 중이며, `java.util.concurrent.locks.ReentrantLock` 사용이 권장됨.
    *   순수 CPU-Bound 작업에서는 플랫폼 스레드 풀 대비 약간의 스케줄링 오버헤드 가능성. CPU 바운드 작업은 여전히 플랫폼 스레드(또는 그 풀)를 사용하는 것이 적합.
    *   `ThreadLocal` 사용 시 주의: 가상 스레드가 매우 많아지면 `ThreadLocal` 변수도 그만큼 많이 생성되어 메모리 문제 유발 가능. `ScopedValue` (Java 20+) 사용 고려.

#### 4.3 Kotlin 코루틴 (Coroutines)

*   **개념**: 언어 및 라이브러리 수준에서 지원하는 **비동기 작업을 위한 경량 실행 단위**. 스레드가 아니라 컴파일러에 의해 변환되는 **상태 머신(State Machine)**에 가까움.
*   **실행 모델**: **`suspend`** 키워드가 표시된 함수(중단 함수 - suspending function) 내에서만 실행이 중단(suspend)될 수 있음 (**협조적 스케줄링**). 중단 시점의 로컬 변수 등 실행 상태는 컴파일러가 생성한 **Continuation** 객체(일종의 콜백 객체)에 저장됨.
*   **`CoroutineDispatcher`**: 코루틴을 어떤 스레드(또는 스레드 풀)에서 실행할지 결정. `Dispatchers.Default`(CPU 작업용 공유 풀, 코어 수 기반), `Dispatchers.IO`(I/O 작업용 공유 풀, 스레드 수 유동적), `Dispatchers.Main`(UI 스레드 - Android 등) 등 제공. 개발자가 직접 스레드 풀 지정 가능. 코루틴은 이 디스패처의 스레드 위에서 실행되지만, 중단 시 해당 스레드를 블록시키지 않고 반환.
*   **블로킹 처리**:
    *   `suspend` 함수는 기본적으로 논블로킹을 가정. `suspend` 함수 내에서 일반적인 블로킹 I/O (예: Java의 `InputStream.read()`)를 직접 호출하면 해당 디스패처의 스레드를 묶어버리므로(blocking the thread), 코루틴의 장점을 살릴 수 없음.
    *   이를 해결하기 위해, 블로킹 작업은 `withContext(Dispatchers.IO) { /* blocking call */ }` 블록으로 감싸서 I/O 전용 스레드 풀에 작업을 위임하거나, 코루틴을 지원하는 논블로킹 I/O 라이브러리(예: Ktor client, Exposed (JDBC 래퍼), R2DBC 클라이언트와 연동)를 사용해야 함.
*   **스택 관리**: 전통적인 스택이 없음. Continuation 객체에 필요한 최소한의 상태(로컬 변수, 중단 지점 등)만 저장.
*   **장점**:
    *   **극도의 경량성**: 메모리 오버헤드 매우 작음 (Continuation 객체 크기 정도, 수십~수백 바이트). 수백만 개 생성 가능.
    *   **매우 빠른 컨텍스트 스위칭 (중단/재개)**: 스레드 전환 없이 상태 객체(Continuation) 복원만으로 재개 가능 (사용자 레벨).
    *   **구조화된 동시성 (Structured Concurrency)**: `CoroutineScope`, `Job` 등을 통해 코루틴의 생명주기, 부모-자식 관계, 취소 전파, 예외 전파 등을 명확하고 안전하게 관리 가능. 개발자 실수 줄임.
    *   비동기 코드를 동기식 코드처럼 읽고 쓰기 쉽게 만들어 줌 (`async/await` 패턴).
*   **단점**:
    *   `suspend` 키워드 및 코루틴 관련 API(Scope, Job, Deferred 등) 학습 필요 (학습 곡선 존재).
    *   기존 블로킹 라이브러리와의 직접적인 호환성 낮음 (래핑(`withContext`) 또는 논블로킹 대체 라이브러리 필요).
    *   디버깅 시 콜 스택 대신 상태 머신과 Continuation 체인을 추적해야 할 수 있음 (IDE 도구 지원 발전 중이나, 전통적 스레드 디버깅보다 복잡할 수 있음).

#### 4.4 성능 및 선택 가이드: CPU 코어 활용 관점

CPU 코어 수의 한계를 극복하고 시스템 자원을 최대한 활용하기 위한 선택:

*   **I/O-Bound 워크로드 (네트워크 요청, 파일 접근 등 대기가 많은 작업)**:
    *   **가상 스레드**: 기존 Java 생태계의 블로킹 코드를 거의 그대로 활용하면서 큰 성능 향상을 얻고 싶을 때 매우 강력한 선택. 캐리어 스레드(플랫폼 스레드) 수를 CPU 코어 수에 맞게 유지하면서 수많은 가상 스레드가 I/O 대기 시 캐리어 스레드를 반납하므로, 코어들이 유휴 상태에 빠지지 않고 계속 다른 작업을 처리할 수 있게 된다.
    *   **코루틴**: 처음부터 논블로킹 I/O 스택(예: Netty, Vert.x, R2DBC, Ktor)을 기반으로 시스템을 구축할 수 있거나, Kotlin 언어를 적극적으로 사용하는 경우 최적의 선택. 극도로 가볍고 구조화된 동시성을 통해 높은 처리량과 자원 효율성을 달성. `Dispatchers.IO`는 블로킹 작업을 처리할 수 있는 충분한 스레드를 관리하여 CPU 코어가 다른 코루틴을 처리하도록 돕는다.
*   **CPU-Bound 워크로드 (순수 계산, 암호화, 데이터 압축 등)**:
    *   **플랫폼 스레드 풀**: 전통적인 스레드 풀 (예: `Executors.newFixedThreadPool(Runtime.getRuntime().availableProcessors())`)이 여전히 가장 직접적이고 효과적인 방식. 작업 수와 스레드 수를 CPU 코어 수에 맞추어 병렬성을 극대화.
    *   **가상 스레드**: CPU 바운드 작업에는 큰 이점이 없음. 오히려 가상 스레드 스케줄링 오버헤드가 약간 발생할 수 있음. 그러나 작업 내에 짧은 I/O 대기가 섞여 있다면 유용할 수 있다.
    *   **코루틴**: `Dispatchers.Default` (CPU 코어 수만큼의 스레드 풀)를 사용하여 CPU 바운드 작업을 병렬 처리할 수 있으나, 작업 분할 및 조합(예: `async`, `launch`)을 잘 활용해야 함. 순수 계산에서는 플랫폼 스레드와 성능 차이 크지 않거나 약간의 디스패칭 오버헤드 가능.
*   **고려사항**: 개발 생산성, 기존 코드베이스 및 라이브러리와의 호환성, 팀의 기술 숙련도, 요구되는 동시성 수준 및 응답 시간 목표, 그리고 시스템이 주로 처리하는 작업의 유형(I/O 바운드 vs CPU 바운드) 등을 종합적으로 고려하여 선택. 핵심은 **제한된 CPU 코어 위에서 얼마나 많은 논리적 작업을 효율적으로 중첩시키고, 코어가 실제로 일을 하도록 만드느냐**이다.

#### 4.5 적용 예: Spring MVC + Virtual Threads

*   Spring Boot 3.0+ (Java 19+ 필요)에서는 `application.properties`에 `spring.threads.virtual.enabled=true` 설정으로 Tomcat 등의 내장 웹 서버가 들어오는 HTTP 요청마다 가상 스레드를 사용하도록 쉽게 구성 가능.
*   각 HTTP 요청은 별도의 가상 스레드에서 처리됨.
*   `@Controller` 또는 `@Service` 내에서 JDBC 호출(블로킹), 외부 API 호출(블로킹) 등 기존의 블로킹 코드를 사용해도, 가상 스레드 런타임(JDK Loom)이 해당 작업 대기 시 캐리어 스레드를 반환하고 작업 완료 시 다시 할당하여 시스템 전체의 동시 처리량을 크게 늘림. 이는 웹 서버의 스레드 풀이 수백 개 수준에서 수만~수십만 요청을 동시에 "처리 중" 상태로 유지할 수 있게 함을 의미하며, CPU 코어는 실제로 실행 가능한 작업에 집중할 수 있게 된다.
*   Spring의 `ThreadLocal` 기반 컨텍스트(`RequestContextHolder`, `SecurityContextHolder` 등)는 가상 스레드 위에서도 (주의사항은 있지만) 동작하도록 지원됨. (Spring Framework 6.1+에서는 `ThreadLocalAccessor` 등으로 전파 지원 강화)

#### 4.6 Amdahl의 법칙과 Gustafson-Barsis의 법칙

CPU 코어 수를 늘려 병렬성을 높이려는 시도는 항상 선형적인 성능 향상으로 이어지지 않는다. 이 한계를 이해하는 데 도움이 되는 두 가지 법칙:

*   **Amdahl의 법칙 (Amdahl's Law)**:
    *   프로그램의 한 부분이 순차적으로 실행되어야 한다면(병렬화 불가능한 부분, P), 아무리 많은 코어(N)를 사용해도 전체 실행 시간 개선에는 한계가 있다는 법칙.
    *   최대 성능 향상 (Speedup) = 1 / ( (1-P) + P/N ). N이 무한대로 가도, Speedup은 1/P를 넘을 수 없다.
    *   예: 프로그램의 10%가 순차적이라면(P=0.1), 아무리 많은 코어를 써도 최대 10배까지만 빨라질 수 있다.
    *   이는 동기화 오버헤드, 공유 자원 접근 제어 등 병렬화하기 어려운 부분이 시스템 전체 성능의 병목이 됨을 시사한다.
*   **Gustafson-Barsis의 법칙 (Gustafson-Barsis's Law)**:
    *   Amdahl의 법칙이 고정된 문제 크기를 가정하는 반면, Gustafson은 더 많은 코어를 사용할 수 있게 되면 문제 크기 자체를 늘려서(더 많은 데이터를 처리하거나, 더 정교한 계산을 하도록) 전체 작업 시간을 유지하면서 더 큰 결과를 얻을 수 있다고 주장.
    *   Speedup_scaled = N - P*(N-1). (P는 전체 실행 시간 중 순차적 부분의 비율)
    *   즉, 가용 코어 수에 맞춰 문제의 병렬화 가능한 부분의 크기를 확장할 수 있다면, 성능 향상 효과는 코어 수에 더 가깝게 비례할 수 있다.
    *   이는 대규모 데이터 처리, 과학 시뮬레이션 등 문제의 크기를 늘릴 수 있는 분야에서 멀티코어 활용의 정당성을 보여준다.

이 두 법칙은 CPU 코어 수의 한계와 그 활용 전략을 고민할 때, 애플리케이션의 특성(순차적 부분의 비율, 문제 크기 확장 가능성)을 반드시 고려해야 함을 알려준다.

### 5. 결론: 상호 연결된 개념들의 조화

운영체제의 기본적인 **멀티태스킹** 원리는 **프로세스**와 **스레드**라는 실행 단위를 통해 구현되며, **OS 스케줄러**는 이들에게 CPU 코어라는 제한된 자원을 효율적으로 분배합니다. 특히 멀티코어 환경에서 스케줄러는 **로드 밸런싱, 캐시 친화성, NUMA 로컬리티** 등을 고려하여 CPU 활용을 최적화합니다. **가상 메모리**는 격리된 실행 환경을 제공하고 **수요 페이징** 등으로 물리 메모리를 효율적으로 관리하지만, 이 역시 TLB 관리나 페이지 폴트 처리 등 CPU 시간을 소모하는 작업입니다.

다중 스레드가 병렬적으로 실행될 수 있는 멀티코어 CPU 환경에서 **공유 자원** 접근 시 발생하는 **경쟁 상태**를 막기 위해 **락**과 같은 동기화 메커니즘이 필수적입니다. 이들은 CPU 아키텍처 수준에서 제공하는 **원자적 연산, 메모리 장벽**에 기반하며, OS는 **futex**와 같은 효율적인 동기화 지원 기능을 제공합니다. Java의 **AQS**나 `synchronized` 키워드의 내부 구현은 이러한 저수준 기술들을 활용합니다. 그러나 락 사용은 **우선순위 역전**이나 **교착 상태**와 같은 복잡한 문제를 야기할 수 있으며, **스핀락**은 CPU 사이클을 낭비할 가능성이 있습니다. **CPU 캐시와 캐시 일관성 프로토콜(MESI 등)**은 공유 데이터의 일관성을 보장하지만, **거짓 공유**와 같은 미묘한 성능 문제를 일으키기도 합니다. 이러한 문제들은 모두 "제한된 CPU 코어에서 여러 작업을 최대한 빠르고 정확하게 처리하려는" 시도에서 파생되는 효과들입니다. **Amdahl의 법칙**은 병렬 처리의 근본적인 한계를 지적합니다.

마지막으로 **가상 스레드**와 **코루틴**은 OS 스레드의 생성 및 관리 비용, 그리고 I/O 대기 시 플랫폼 스레드(결국 CPU 코어에 매핑되는)의 비효율 문제를 해결하여, 제한된 CPU 코어 위에서 수많은 동시 작업을 효과적으로 처리할 수 있는 현대적인 접근 방식을 보여줍니다. 이들은 OS 스레드를 직접 많이 만드는 대신, 소수의 플랫폼 스레드 위에서 수많은 경량 작업을 스케줄링함으로써 CPU 코어의 실제 작업 시간을 극대화하려 합니다.

이 모든 개념은 시스템의 성능, 안정성, 응답성을 결정하는 데 서로 깊이 연관되어 있으며, 특히 **CPU 코어 수의 한계와 그로 인한 작업 분배 및 동기화의 필요성**이라는 관점에서 이를 종합적으로 이해하는 것이 효과적인 시스템 설계와 프로그래밍의 핵심입니다.
